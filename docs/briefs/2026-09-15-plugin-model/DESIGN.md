# Consolidated design

## 1. One plugin model

A plugin contributes any supported Korri seams. It can supply runners,
families, catalog records, discovery, acquisition, launch modifiers,
services, or controls. It need not supply a runner.

All plugins have the same contract. `@korri` means first-party maintenance
and testing, not a privileged ABI. A different publisher can provide the
same kinds of integration.

A source plugin normally has:

```text
flake.nix       build inputs and outputs
flake.lock      exact input revisions
plugin.ts       declaration and executable operations, when needed
src/            optional ordinary helper modules
```

`plugin.ts` is the entry name. Use ordinary imports after that. Authors do
not concatenate source files or strip `export` with string replacement.
A source generator can produce the complete plugin.ts; a generated output
does not need its own source directory or separate flake.

`nix flake lock` creates the lock without building. Publishing uses the
committed lock. `nix build --no-update-lock-file` prevents a build from
silently updating it. A lock is not generated by Korri on the device.

## 2. Source contract

The module exports ordinary data and a `handlers` map. Static exports
include identity, schemas/defaults, records, and operation declarations.
Executable operations are functions in that map.

The same exports apply to hand-written, helper-composed, and generated
plugins. There is no special `delta` fragment format.

Module initialization constructs declarations without I/O. Runtime choices
and state-dependent descriptions come from explicit operations. The host
can evaluate the module to check bindings without starting a download,
changing user files, or launching a game.

Runtime information includes controller lists, supported display modes,
installed games, runtime-generated settings, and current control availability.
The operation contract admits these; it does not pretend all metadata is
known at build time. Runtime results cannot silently change plugin identity
or replace the package's source code.

## 3. Operations rather than one special launch function

`launch.prepare` is the proposed name for what earlier examples called
`run()`. `preferences.map` replaces the earlier separate preferences callback.
All executable operations use the same context shape, with operation-specific
request/result types. See OPERATIONS.md and plugin-contract.ts.

This is one ABI with optional operations, not a requirement for every plugin
to implement every function. A fixed native-game launch can remain data-only.
A service plugin can contribute a systemd unit without launch code.

## 4. Nix inputs and outputs

Every independent source plugin uses a flake. No particular builder library
is compulsory. Dependencies remain Nix dependencies.

One flake may expose:

```text
packages.aarch64-linux.default    @korri:retroarch, family integration
packages.aarch64-linux.mgba       @korri:mgba
packages.aarch64-linux.snes9x     @korri:snes9x
```

Each output is a separate plugin: identity, receipt, approval, enablement,
update, and removal. Nix shares identical store paths. Different RetroArch
builds coexist. Installing a family plugin never substitutes its binary or
renderer into a runner built with another revision.

Attribute presence does not prove platform support. The catalogue needs
explicit supported-platform metadata and per-target build checks. Core
library filenames must be explicit or obtained from reliable package
metadata, not guessed from pname. File extensions alone do not prove a
system: ambiguous formats remain candidates, not alphabetical winners.

The base OS does not include RetroArch merely because it supports plugins.
Devices pull built closures; they do not compile games or plugin dependencies.
An aarch64 package output uses a suitable builder. Its name does not imply
cross-compilation. Nix build dependencies can include regressions and evidence
checks; these do not all have to be runtime files.

## 5. Artifact: proposed single generated manifest

Authors maintain TS and Nix. The recommended output is:

```text
manifest.json             static declaration, operation names, files, source inventory
plugin.ts                 entry, if code/declaration source is shipped
src/...                   imported source
node_modules/...          optional shipped packages and package.json files
```

No mandatory plugin.yaml, declaration.json, or precompiled plugin.js.
A data-only plugin can have no source entry if its build produces a complete
manifest and it has no runtime handlers. An optional JS bundle remains a
packaging optimization, not a distinct plugin contract.

The manifest is generated, not another authored copy of the same data.
It contains:

- contract version and plugin ID;
- static declaration extracted from the effective module or generated data;
- handler operation names (never serialized function values);
- entry name and explicit inventory of admitted source files;
- named immutable artifacts, units, and requested ports where applicable;
- requested host-service access and settings-contract metadata.

The host checks static extraction against the effective module at admission.
Metadata extraction is not an invitation to read user state during the build.
Dynamic describe/options results are not frozen into this manifest.

The source inventory includes relative imports and package-resolution files.
The builder copies the selected dependency graph into the artifact (or a
clearly admitted graph); a bare import is not a request for network fetching.
Named executable/data paths retain Nix string context so their closures are
real. The module source inventory and binary file map serve different roles.

### Current loader fact

The code at main 0a30ad4ef2afca75f46d87a79344b07ac1a72978 has Oxc in-process
TS transpilation and a prepared graph loader. However,
`script/source.rs::package_plugin` registers only `plugin.ts` today.
The package producer/admission path must be extended to supply the graph.
The engine support is not proof that installed plugins already import every
shipped file. Dynamic imports and general Node/Bun APIs remain unsupported
for now. See IMPLEMENTATION.md.

## 6. Shared RetroArch integration

Recommendation: name it `@korri:retroarch`, since its config language,
renderer, defaults and frontend are RetroArch-specific. libretro remains
the core API. Folder: `retroarch/`; optional TS library: `@korri/retroarch`.
The earlier name `@korri:libretro` was a proposal, not a deployed migration.
If existing user data uses it, provide an explicit migration, not two
silently equivalent IDs.

The SAME plugin flake can provide:

1. An installable family plugin with schema/default descriptions and UI/control
   contributions.
2. Optional Nix functions that build complete core plugins.
3. An importable TS library with the schema, mapping, renderer and operations.

This is still one plugin model. A library export does not create a special
class of plugin. Another publisher can supply an equivalent helper.

### Two ways to opt in

Build-time: use the flake/TS helper. The consumer carries the selected
frontend, source and dependencies in its closure. The family owner comes
from the helper declaration, not the consumer namespace: @local:mgba can
claim @korri:retroarch without inventing an @local:retroarch family.

Runtime integration: declare family `@korri:retroarch`. This selects shared
user-settings scopes and optional family UI/control descriptions. It is a
compatibility claim, not a receipt dependency or semantic proof.

The runner contains a usable schema, effective defaults, and launch handler.
It runs without a separately enabled family package. Family settings still
apply and are checked against that runner. Enabling the family package adds
family-level presentation and compatible controls; it does not inject new
launch defaults or code into an existing runner.

A family control is offered only when the active runner advertises a
compatible action. Execution goes through that runner's session-control
operation or owned native adapter. A label is not an implementation.

### Versions coexist

A runner built with revision A keeps A. A family plugin or another runner
using revision B can coexist. No replacement is required. An installed
family's newer description cannot expand the active runner's capabilities.

Use a small settings-contract version (recommended) to identify incompatible
changes in names/units. It is NOT a Git revision. Family membership alone
never proves compatibility. Unsupported keys are retained and diagnosed.

## 7. Core authoring and generation

One catalogue maps core name to derivation, actual library path, supported
systems, platform support, discovery hints, and an optional plugin.ts.
The generator emits one normal plugin per entry, not a special thin-plugin
kind. There is no requirement to install the shared frontend separately.

The no-customization case needs only a catalogue entry. The core-specific
case adds an ordinary plugin.ts exporting settings/defaults/handlers.

A helper accepts an explicit RetroArch derivation override. It is an ordinary
Nix function, not a NixOS module. Selecting a different frontend build does
not require abandoning the helper. Associated config checks must use that
selected build. A fork with a different API can instead use a full DIY plugin.

Composition rules (recommended):

| Export | Rule |
|---|---|
| Effective identity | Defined once; conflicting sources fail the build |
| Defaults | Deep-merge library then author's defaults |
| Schemas | Extend fields; conflicting definitions require explicit replacement |
| Handlers | Author's handler replaces inherited handler for that operation |
| Records | Merge by ID; unresolved ID collisions are errors |
| Arrays | Replace unless the field explicitly defines accumulation |

No implicit function chaining. An author can import and call the shared
handler when desired. Generated code must preserve all declared seams, not
silently discard controls, providers, or discovery that the author added.

Schemas describe settings. Mapping to native keys belongs to the helper,
not application-specific branches inside korrid. Native/core config files
are distinct artifacts; never load an .opt through --appendconfig merely
because both happen to use key=value syntax.

## 8. Sessions, wrappers and native code

Korri owns launch/session identity and lifecycle. Plugins return plans,
observations, and host-tracked resource handles. The host starts the selected
process, associates helpers with the session, and performs cleanup after
normal exit, cancellation, timeout, or failed startup.

Modifiers are an explicit ordered list. Composition handlers run in listed
order: plan -> modifier 1 -> modifier 2 -> final plan. If each wraps the
previous command, the LAST modifier becomes the outermost process.
Example: Box64 then Gamescope yields Gamescope(Box64(game)). This is not
installation order or alphabetic order. Duplicate selections are rejected
unless the modifier explicitly supports repeated instances.

Show the base plan, every composition step, final argv/env, selected store
paths, contributing settings and diagnostics. Redact credential values.
A process exit before a ready callback still triggers generic cleanup.
Cleanup is idempotent, best-effort, and cannot skip other resources when
one cleanup action fails. It must not delete persistent saves.

Nix provides immutable bytes. Mutable Wine prefixes, extracted user content,
firmware/key readiness and installed-game status require runtime preparation
or installation operations. Packaging them is not the same as provisioning
them. Native wrappers remain allowed; their effects must be owned and
reported, not assumed absent because the descriptor is data-only.

## 9. Data and updates (recommended details)

Use separate locations for immutable sources, reconstructible caches,
plugin state, session temporary files and persistent user saves.
Updating a plugin preserves data. Removing it preserves saves and user
settings unless the user explicitly requests deletion. Unsupported settings
are not removed during a downgrade.

A running session retains its package generation and Nix GC root until it
ends. An update changes future sessions, not code halfway through a game.
Do not assume save states can be exchanged between cores or core versions.
Keep save-state compatibility metadata; never automatically overwrite an
incompatible state. Persistent save identity is distinct from package
version. Exact on-disk naming is an implementation detail that must preserve
those invariants, not derive identity from display titles.

## 10. Proportionate trust

This is an entertainment system with trusted installed plugins. Keep simple
validation, clear grants to host services, bounded operations and safe file
ownership. Do not add family attestation, approval per closure dependency,
or claim namespace strings or signatures prove behavior is safe.

Show trust/service requests when installing or enabling, not at every launch.
Keep secrets out of declarations, Nix outputs, shared YAML and normal logs.
Native code still runs under the selected user/service process policy.
No claim that TypeScript types or permission metadata creates a sandbox.

Testing is deferred by agreement. This document specifies behavior; it does
not assert that the old examples implement it.
