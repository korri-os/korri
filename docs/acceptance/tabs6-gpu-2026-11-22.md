# Tab S6 GPU hang investigation, 2026-11-22

Source: `22b19b583` (main `88e89c9eb`, GameSir rearm `d626276cf`, Kishi
`22b19b583`). Device: SM-T860, Linux 7.3.4, native MSM/DPU, A640,
Mesa 26.2.3, Sway and the FemtoVG shell. No panel or kernel change.

## Verified cause and limit

The shell's default GMEM rendering path triggers GPU CCU translation faults.
The devcoredump names `korri-sh:gdrv0`, revision `06040001`, READ,
TRANSLATION, source CCU. One fresh idle boot faults at monotonic 32.876 s
at IOVA `0x1145d0000`, then recovers at 32.977 s. This precedes a game
launch: Gamescope and RetroArch are not necessary to trigger the fault.

`FD_MESA_DEBUG=sysmem` on **korri-shell only** bypasses GMEM while keeping
hardware OpenGL rendering. It prevented the GPU fault in two boots, including
shell rendering, launching Super Mario World, and returning to the shell.
Disabling GEM eviction and disabling UBWC separately did not prevent it.
Mesa 26.3.0 also faults, with its library confirmed in the process maps.
That experiment needed its matching glibc loader: the installed shell's
older libm cannot load 26.3.0 (`GLIBC_2.43` missing).

This is a device-local mitigation, not a proven fix to the underlying
Mesa/kernel command-stream bug. The exact failing GMEM operation remains
unknown. Its cost is higher memory bandwidth in the shell. Games and the
compositor retain their normal rendering path.

restarting the shell without verbose DRM logging still reproduced both
negative experiments.

## Gameplay and remaining faults

On `699953d8`, two captured Mario frames differ and Simon confirmed that the
title demo moved. On the second sysmem boot, Mario instead stopped after its
initial frame. Six screenshots over 30 seconds are identical; GDB finds the
main thread waiting in `pulse_write` / `pa_threaded_mainloop_wait`, not in
Mesa. ALSA reports RUNNING but its `hw_ptr=480` and timestamp do not advance
between reads two seconds apart. In the working boot the hardware pointer
advanced normally. This is a separate audio-clock stall; GPU mitigation
alone does not establish reliable gameplay.

Atomic EBUSY errors also remain without any GPU recovery. The moving demo
proves they do not always mean a stuck display. DPU status shows both bonded
links in command mode and zero underruns. Their cause is unresolved; do not
claim that the sysmem mitigation fixes the DPU commit path.

## Deployment and verification

Built source `9ad032a1b` and deployed with `--reboot`. The installed system is
`/nix/store/24dygz3rhxysd4wmakj4pxnnzp3wv5r6-nixos-system-tabs6-26.11.20260923.4975466`.
The active bundle is the system's expected
`/nix/store/1m94qkyd9z0lbmwnf494gx7ky62w5hd3-korri-bundle-0.0.0`, and the
running korrid executable matches it. The kernel is unchanged (`qd387z…`).
The temporary systemd override was removed before deployment; the system's
own shell unit now supplies `FD_MESA_DEBUG=sysmem`. The first deployed boot
was blessed, and the next reboot ran the same system.

Both deployed boots still reproduce the independent audio stall: identical
Mario screenshots and an ALSA hardware pointer stuck at 480. Gameplay is
therefore **not accepted as reliable**.

The Kishi deployment log confirms why bundle selection was missed: it used
`installing (boot)`, exited successfully, and printed a manual selector
command. A product deploy without `--reboot` now switches the system and
bundle together. Verification checks the running executable even when the
active symlink already matches. A stale executable causes a deploy failure;
the selector itself does not restart an already-selected bundle.

A real no-flag redeploy reached the new `switch` path but exited 4 before
selection because the existing `korri-limits.service` fails to write
`/sys/fs/cgroup/korri.slice/cpu.uclamp.min` (ENOENT). This was not hidden or
reported as success. The bundle already matched. The missing kernel uclamp
support is a separate follow-up and also explains the launch-limits warning.
The `--reboot` deploy completed successfully.

Checks passed: the tabs6 module assertions, seven deploy-command tests,
ShellCheck, Nix formatting, Python syntax compilation and secret-scan hooks.
The new environment assertion failed before the GPU configuration change.

Raw journals, devcoredumps, process maps, backtraces and screenshots were
captured on the build host in `/tmp/tabs6-gpu-evidence/`, with a compressed
copy at `/tmp/tabs6-gpu-evidence-2026-11-22.tar.gz`. They are not shipped.
