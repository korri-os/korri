# RG353M complete controller input (#478) — 2026-11-14

## Change

Commit `84ea942a1b257539f3e43c57aaa8035225708f00`, followed by
`3bd75c255f29812bd6f3bdb847884196431481fe`, adds the native
`adc-joystick` to the existing InputPlumber composite. The four physical
sources merge into one xb360 target before inputd captures it and forwards
whole controller state to the shared seat receiver.

Inputd accepts one keyless source whose axes are a non-empty subset of
X/Y/RX/RY, beside one gamepad with disjoint axes. All 15 non-empty subsets are
tested, including the candidate X/Y-only RG DS shape. A second stick source,
overlapping axes, keys on a stick source, axes outside that set, and
unclassifiable auxiliary sources remain ambiguous. Sticks alone are not a
controller. The RG DS profile is unchanged and has not been verified on hardware.
The extra all-device identity-topology guard in the first commit was removed;
existing physical discovery remains responsible for topology acceptance. The button pad keeps reconnect
identity `gpio-keys/input0`. No persistent schema or controller identity is
added.

## Board calibration and kernel correction

Commit `5ff83d91faed3ff8d96cddfdbf38814f199f5871` adds a board DT overlay
and builds only `adc-joystick.ko` against the unchanged Linux 7.2 kernel. It
follows the existing out-of-tree panel-module pattern. No full kernel rebuild
or image write is involved.

Labelled holds established the old error:

| Hold | Old adc-joystick | Old Seat P1 |
|---|---:|---:|
| Left UP | ABS_Y 906 | +25160 |
| Right UP | ABS_RY 935 | +27045 |

Linux `Documentation/input/gamepad.rst` requires positive Y downward. Both
old Y signs were wrong at the kernel boundary. The map, xb360 target, and
inputd preserved that sign; none receives a compensating board-specific flip.
X was correctly negative to the left. The isolated RIGHT hold produced
positive RX, which is correct.

The 60-second self-paced ADC/raw/pad/seat capture measured full circles and
rests. Rest phases were selected from values, not assumed cue times.

| Axis | IIO extrema | Rest median | New DT abs-range | New evdev bounds |
|---|---:|---:|---|---|
| X | 101–971 | 566 | 960 170 (inverted) | 170–960 |
| Y | 54–935 | 493 | 915 75 (inverted) | 75–915 |
| RX | 86–949 | 509 | 90 930 | 90–930 |
| RY | 95–938 | 507 | 105 905 | 105–905 |

These bounds center the axes near the measured rests and reach full scale at
the end stops. The cost is clipping angle-dependent mechanical overtravel,
particularly the X circle's lower electrical extreme. They are measurements
of this haku, not a claim about every unit's calibration.

The kernel driver had a second bug: both polled and buffered paths passed the
channel index to its inversion helper instead of the ABS code. With channel
order X/RX/Y/RY, inverting left Y looked up unconfigured ABS_Z bounds. The
patch uses the actual ABS code and clamps to the DT calibration bounds. The
clamp prevents overtravel from escaping the advertised range and overflowing
the downstream signed controller value.

The regression harness compiles and runs the actual selected driver functions
with in-memory IIO/input adapters. It checks both paths, all 16 inversion
combinations, non-sequential ABS codes, distinct ranges, centers, endpoints,
and out-of-range readings: 640 axis checks. It failed on the original source.
The native ARM module build passes it. The new `rg353m-input` Nix check reads
the selected merged DTB and the shipped module ABI, not only overlay text.
The existing MPP/DTB check still passes.

### ROCKNIX grounding

Reference: legacy `product/systems/nixos/images/platforms/rocknix-rk3566.nix`,
ROCKNIX RK3566 patch `0005-arm64-dts-rockchip-fixup-anbernic-controls.patch`,
and `rocknix-singleadc-joypad.c` at
`7647fdb0fc89cd69b284903bf7707e861df5dc7e`.

Mainline's GPIO mux has two active-low select pins. Its channels X/RX/Y/RY
correspond to ROCKNIX's channel indices 3/1/2/0. Thus ROCKNIX's X/Y inversion
and un-inverted RX/RY agree with the corrected directions. The selected RG353P/shared
DT produces the wrong Y directions on this RG353M. This is not evidence that
other RG353 variants need the same change. The channel-index inversion lookup
is a separate, confirmed upstream ADC driver bug.

ROCKNIX advertises ±1800 after its scale=2, calibrates the center on open,
applies a radial deadzone, multiplies by 2.45, then clamps. Its tuning factor
is not a multiplier to copy into the mainline 10-bit DT range. Mainline's
observed span already covers roughly 84–87% of its former 15–1023 interval.

Flat remains 32 raw counts. Fuzz becomes 4 raw counts: short steady-state
jitter was about ±2 counts, whereas 32 hid fine motion and held end-stop
reports well short of the electrical endpoint. Center drift across the
capture remained inside flat=32 and the seat's existing neutral margin.

### Polling and CPU

A private function-graph trace measured the actual ADC callback, with sleep
time excluded and zero buffer overruns. No target code was compiled. The
private trace instance was removed and the original runtime poll restored.

| Configured poll | Actual callbacks/s | Callback CPU, % of one core |
|---|---:|---:|
| 60 ms, two 10-second windows | 15.40, 15.50 | 0.317, 0.316 |
| 10 ms, two 10-second windows | 59.09, 60.09 | 1.092, 1.076 |
| New module/DT, 10 ms | 60.29 | 0.948 |

HZ=250 and ADC read/settle work explain why configured 10 ms is not 100 Hz.
The chosen 10 ms matches ROCKNIX and cuts the measured sample period from
about 65 ms to about 17 ms. The old-module A/B adds 0.77 percentage points of
one core, equivalent to 0.19% of this four-core CPU. These are callback CPU
costs, not all IRQ/application work. On the deployed new system at rest,
InputPlumber used 6.47% and inputd 1.18% of one core in a 15-second window.
The existing reach-signalling CPU problem is outside this change; korrid used
111% of one core in that window.

## Layer contract

| Layer | Positive direction / sign | Stick range | Sampling/delivery |
|---|---|---|---|
| DT/kernel | X/RX right; Y/RY down | Calibrated bounds above, flat 32, fuzz 4 | 10 ms configured, about 60 callbacks/s measured |
| adc-joystick evdev | Same Linux convention | Sorted per-axis DT bounds; clamped overtravel | Changes after kernel fuzz filtering |
| InputPlumber map | Same sign; no inversion/tuning | Linear normalization to -1…+1 using evdev min/max | Event-driven, no new sampler |
| xb360 target | Same Linux convention | -32768…32767; fuzz 16, flat 128 | Event-driven; may emit several SYN frames per poll |
| Korri Seat P1 | Same signed values as xb360 | -32768…32767; fuzz 0, flat 4096 | Whole-state/delta forwarding; no axis rate limiter |
| Moonlight evdev | Linux input; wire Y becomes up-positive for XInput | Signed 16-bit, seat flat removed/rescaled | Event/SYN-driven; wire packet rate not measured |

Moonlight's ordinary Linux-to-XInput Y conversion is not a board correction.
Its `evdev_convert_value` reverses Y and removes the reported flat region.
No Moonlight map, inputd conversion, or InputPlumber map was changed to hide
the kernel's wrong directions.
