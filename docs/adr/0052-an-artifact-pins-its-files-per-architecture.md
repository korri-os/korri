# An artifact pins its files per architecture

**Owner decision, 2026-11-08.** One artifact ID can carry a different pinned
file set for each architecture. A device acquires only the file set for its
own architecture. When an artifact has no file set for that architecture, the
device skips it, and a runner that lists it starts without it.

The case is Steam on aka (`x86_64-linux`), which must run as the same single
`@korri:steam` plugin as on the RP Mini V2 (`aarch64-linux`). Today
`@korri:proton/cachyos` pins only the arm64 Proton-CachyOS tarball, and
`@korri:fex/rootfs` is needed only on arm64. With this decision the Steam
runner keeps one `artifacts` list on both architectures. Proton pins an arm64
and an x86_64 build under its one ID. FEX pins its rootfs for `aarch64-linux`
only.

Grounding: the architecture names are the Nix system strings that the plugin
catalog already uses for a release's `platform`
(`services/korrid/plugin-host/src/catalog.rs`). ADR 0047 already gives each
native plugin one release per architecture. This ADR extends the same split to
the artifacts in ADR 0012.

Shape (owner delegated the choice, 2026-11-08: "best long term approach"): an
artifact record keeps `id`, `unpack` and `title`, and has either `version` and
`files` (the same on every architecture) or `platforms`, a map from Nix system
to `{version, files}`. Each architecture carries its own version, because
upstream builds for different CPUs are separate releases that can drift apart.
The cache path stays `cache/<plugin>/<key>/<version>/`, and the Mini's Proton
version and tool name stay unchanged. A skipped artifact is absent from
`PluginLaunchInput.artifacts`, exactly like a runner that never listed it.
`services/korrid/SCRIPTING.md` holds the full rules.

## Considered options

- Two artifact IDs, with the runner choosing one at launch. Rejected: korrid
  would download both unless it skipped one, so it needs the architecture
  anyway, and every runner repeats the choice.
- A build-time declaration for each architecture, generated by `plugin.nix`.
  Rejected: `plugin.ts` would stop being the single source of the pin, and
  the catalog would carry two declarations for one plugin.
