# PPSSPP

A whole emulator, written by hand, that borrows nothing from the catalogue.

| File | What it holds |
|---|---|
| `plugin.ts` | The declaration and the `launch.prepare` handler |
| `plugin.nix` | One package and one named file |

## Why it exists

This plugin is a proof. The libretro cores share a family, a generated
`plugin.ts`, and a launch helper, and it would be easy to assume some of that is
what makes a runner work. It is not. PPSSPP joins no family, imports no helper,
and is generated by nothing, and it is built by the same builder and admitted by
the same rules as `korri-plugin-mgba`.

`services/korrid/tests/diy_runner.rs` holds that proof: the runner registers
with no family record present anywhere, resolves its own program from its own
package, claims `.iso`, `.cso` and `.pbp`, and produces a launch plan.

## What it does not get

No session controls. Effects are a closed first-party vocabulary implemented by
korrid for RetroArch and Moonlight, so a runner outside those two declares none.
PPSSPP does not answer the RetroArch network command protocol, and claiming a
RetroArch effect to get a menu would aim commands at a process that cannot
reply. See `services/korrid/SCRIPTING.md`, "Effects are a closed first-party
vocabulary".

No typed settings. `settings.describe` and `settings.validate` are real
operations a runner may implement, and this one does not yet. It therefore
refuses authored settings and raw config overrides rather than accepting them
and dropping them silently.

Both gaps are the honest current state, not a limit of the contract.
